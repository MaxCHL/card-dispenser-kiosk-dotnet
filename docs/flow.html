自助報到發卡流程

飯店自助報到機串接自動發卡機(Card Dispenser):卡匣堆疊數百張空白 Mifare Classic 卡,由馬達逐張推出,途中完成讀卡判斷 → 寫入房卡資料 → 回讀驗證, 再送給旅客。真正的難點不在 happy path,而在每一步都可能失敗時, 機器如何安全收斂——重試、吞卡換卡、還是停機告警。

Fallback 矩陣

設計審查時最常被追問的就是這張表:每種故障怎麼偵測、當下怎麼處置、系統往哪裡收斂。 原則是——機械類失敗謹慎重試、卡片類失敗吞卡換卡、資源類耗盡直接停機,絕不盲目動作。

故障情境偵測方式處置收斂結果
卡匣空 庫存 sensor + 計數為 0 中止 不推卡 通知櫃檯補卡
推卡未到位 / 卡住 推卡後閘門 sensor 逾時未偵測到卡 重試 有限次重推;仍失敗 → 停機 Jam 告警,人工排除(避免疊卡)
讀卡失敗 / 非空白卡 讀不到 UID、型別未知、或非可用空白卡 重試 重讀;仍失敗 → 吞卡換卡 問題卡進回收艙,換下一張重來(對旅客無感)
寫卡失敗 / 驗證不符 authenticate 失敗、寫入錯誤、或回讀比對不一致 重試 重寫;仍失敗 → 吞卡換卡 瑕疵卡進回收艙,換新卡(不可把寫壞的卡發出去)
旅客逾時未取卡 出卡後等待逾時,出卡口 sensor 仍偵測到卡 吞卡回收 基於安全收回 + 記錄,通知櫃檯協助
回收艙滿 吞卡前檢查回收艙 sensor 停機 不硬吞 告警,需清艙後才能繼續
換卡超過上限 單筆交易累計換卡數達上限 中止交易 告警,避免讀寫連續失敗把卡匣吞光
機台通訊逾時 與發卡機指令 / 回應逾時 安全狀態 收斂中止 不卡死流程,回報上層由人工或重啟處理
卡片格式

房卡資料寫在哪

飯店智慧門鎖常走 13.56MHz 高頻卡,以 Mifare Classic 為主、DESFire 部分支援。 讀寫前要先對 sector 認證,房卡資料寫進指定的 data sector。

Mifare Classic 1K

16 sector × 4 block × 16 bytes。每個 sector 的最後一個 block 是 sector trailer,存 Key A + access bits + Key B;讀寫該 sector 前必須先用 Key A 或 B authenticate。sector 0 的 block 0 是製造商區(UID),唯讀。

下圖為單一 data sector 的 4 個 block:前三塊放房卡資料,最後一塊是控制存取的 trailer。

block 0房號・效期
block 1門禁權限
block 2CRC16 校驗／備用
block 3Key A · AC · Key B

DESFire(部分支援)

資料以 application → file 組織,支援 AES/3DES 雙向認證與 檔案級權限,安全性高於 Classic。本模擬用輕量抽象表示,已實作 AES128 的 3-pass 挑戰-應答互相認證與 session key 衍生(見 Part C),通過認證後才可讀寫 file;CMAC、command counter、secure messaging 與完整 application/file 權限矩陣則刻意省略。

為何辨型別重要:讀卡階段要先判斷是 Classic 還是 DESFire,才知道用哪套認證與寫入方式; 判斷錯誤會直接導致認證失敗,落入吞卡換卡分支。

安全提醒:Mifare 出廠預設 key FFFFFFFFFFFF 是公開值,正式環境務必做 key diversification(每卡/每案場衍生不同金鑰),否則等同無保護。

離線鎖 · data-on-card 擬真模型

離線 data-on-card 驗證

飯店離線鎖(autonomous lock)是離線的:門鎖不連網,權限與效期寫在卡片上, 鎖用自己的時鐘離線驗證。退房不必碰鎖——新卡的遞增序號在鎖首次讀到時就把舊卡蓋掉。

離線驗證的 6 道關卡

  1. 已佈建? 鎖是否已用母卡設定過(否則一律拒絕)
  2. 簽章有效? 用案場 SiteKey 驗 MAC,擋竄改與異案場卡
  3. 案場相符? PropertyId 與本鎖一致
  4. 在效期內? 鎖 RTC 落在 from–to 之間(過期／未生效即拒)
  5. 門權限相符? 房號／門群涵蓋本門
  6. 序號夠新? seq ≥ 鎖記錄值,通過後更新記錄(舊卡即失效)
誠信提醒
飯店電子鎖廠商的 encoder SDK 通常未公開文件,本頁與程式的 encoder 介面以 代表性抽象模擬,非任何廠商的真實專有 API。採用的是可查證的產業通用架構模型:離線 autonomous 運作、 Mifare Classic + DESFire、設定卡佈建門鎖、飯店 PMS + API 整合。

模擬 vs 正式硬體

附帶的 C# 程式把整條流程與所有 fallback 用「故障注入」跑給人看; 換成真實機台時,架構不變,只是把模擬硬體換成廠商指令集。

維度本模擬正式硬體

庫存偵測記憶體卡堆疊 + 計數實體卡匣 sensor + 後端庫存服務對帳
卡片金鑰出廠預設 FFFFFFFFFFFFkey diversification,金鑰由 HSM／KMS 管理
感測回饋布林旗標模擬 sensor閘門／出卡口／回收艙多組實體 sensor
交易記錄Console logPMS／後端寫入,含發卡稽核與異常告警

附帶的可編譯 C# 模擬(.NET 10)以 ICardDispenserHardware 抽象硬體,用故障注入逐一重現上圖每一條 fallback 路線——正常發卡、卡匣空、讀失敗換卡、 寫失敗換卡、旅客未取回收、卡住停機。Mifare Classic 卡結構與認證亦在其中建模。
